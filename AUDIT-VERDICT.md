# Audit Verdict: buddypress-favorite-notification

**Branch:** 2.0.0 (post QA-card-fix push) | **Method:** Static only, read-only (no browser, no edits) | **Date:** 2026-07-03

## Shippable? WITH FIXES
The recent QA fixes (N+1 elimination on the who-favorited modal, dark-mode support for the liked-by display, instant refresh, dead-module wiring, native-confirm removal) all landed correctly and hold up under static review. But this pass surfaced one **new-to-this-branch dead-toggle bug** (a Settings-tab checkbox that does nothing) that must be fixed before release, plus a large mass of orphaned legacy JS that should be pruned rather than shipped again.

## Sellable? WITH POLISH
The favorite-display feature (the plugin's core value prop) is solid: paginated/bounded queries, cached, batch-fetched, dark-mode aware, correctly nonce-gated. But roughly half of `assets/js/admin.js` and all of `assets/js/notifications.js` are inert legacy code with no matching PHP handlers or matching DOM — that's not "sellable" polish, it's leftover scaffolding a paying customer's browser downloads for nothing.

## Verified clean (no action needed)
- **Favorite-display AJAX (`bpfn_get_all_favorites`, `bpfn_refresh_favorite_display`)**: both correctly `check_ajax_referer('bpfn-favorite-nonce')`-gated, intentionally public/`nopriv` (read-only), match their PHP handlers 1:1, and are wired end-to-end JS↔PHP.
- **Big-site readiness — who-favorited list**: `get_users_who_favorited()` uses `LIMIT`/`OFFSET` (never unbounded), a filterable cap (`bpfn_who_favorited_limit`, default 50, was 999), `cache_users()` batch-priming (eliminates the N+1 the plugin's own CLAUDE.md flagged), 5-minute object-cache TTL with correct invalidation on add/remove, and a dedicated `COUNT(*)` for the total instead of counting a fetched array.
- **Admin dashboard trending/recent tables**: capped at `LIMIT 10`, wrapped in a 5-minute transient invalidated on favorite add/remove, and batch-resolve activities (`bp_activity_get( in => $ids )`) + users (`cache_users()`) up front instead of per-row queries — N+1 risk flagged in the stale manifest is resolved.
- **Capability/nonce coverage**: all `manage_options`-gated admin AJAX handlers check nonce + capability; `check_ajax_referer` dies by default so ordering relative to the cap check is not exploitable.
- **Escaping**: spot-checked output in `favorite-display.php`, `overview.php`, `notification-item.php`, email templates — consistent `esc_html`/`esc_url`/`esc_attr`/`wp_kses` usage, no raw `echo` of unescaped user/DB data found.
